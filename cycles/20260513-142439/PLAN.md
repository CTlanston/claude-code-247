The canary-token leakage scan is the 7th and final documented
S-L7 safety gate. Its purpose: detect when canary tokens (test
secrets the operator plants in commits, environment, or input to
flush out leaks) appear in output the system might write back to
logs, audit trails, or stdout — closing one class of secret-leak
risk.

## Change being made

1. **`orchestrator/canary_scan.py`** (new):
   - Define a canary pattern `r"AUTODEV_CANARY_[A-Z0-9]{8,}"`.
     This is a deliberate, well-known prefix the operator can
     use to plant canaries; the scanner only flags strings
     matching this shape, NOT arbitrary high-entropy data
     (which would generate false positives on hashes,
     git SHAs, base64, etc.).
   - `scan_text(text: str) -> list[str]` — return all canary
     tokens found in `text`, in order, deduplicated by first
     appearance.
   - `scan_file(path: Path) -> list[tuple[int, str]]` — walk a
     file by line, return `(line_number, canary)` matches.
     Binary files / unreadable files → empty list (never
     raises).
   - `scan_paths(paths: Iterable[Path]) -> list[tuple[Path, int, str]]` —
     iterate over multiple files; flatten to
     `(path, line_number, canary)` records.

2. **`tests/test_canary_scan.py`** (new):
   - Pattern + module are importable, `CANARY_PATTERN` exported
   - Empty text → []
   - Text without a canary → []
   - Single canary match → 1 result
   - Multiple canaries in one text → all in order (dedup
     preserved-first-appearance)
   - Common-shaped non-canary strings (lowercase prefix,
     `AUTODEV_CANARY_short`, mixed case) NOT matched
   - `scan_file` on a tmp file with a canary → 1 result with
     correct line number
   - `scan_file` on missing file → [] (no raise)
   - `scan_file` on a binary file with embedded canary →
     [] (gracefully skipped on UnicodeDecodeError)
   - `scan_paths` flattens correctly across multiple files
   - The keyword `canary` is in the test file (compute_level
     marker grep)
