## Why a narrow pattern (instead of high-entropy detection)

Considered three approaches:

1. **High-entropy heuristic** (e.g. Shannon entropy > X):
   Rejected. False-positive on hashes, hex git SHAs, base64
   blobs, JWT tokens that aren't actually secrets, etc.

2. **Configurable allowlist of regexes** (operator supplies
   their canary patterns):
   Rejected for this cycle. Adds config complexity without
   demonstrated need. Can be added incrementally later.

3. **Single narrow opt-in pattern** (`AUTODEV_CANARY_<HEX>`):
   **Chosen.** Zero false positives, zero config, clear
   contract. The operator plants canaries with the exact
   prefix; the scanner finds exactly those.

If the threat model ever expands to detecting credentials in
the wild (real GitHub PATs, etc.), that's a separate Track —
this cycle covers the narrow but useful canary-planting case
the rubric documented.
